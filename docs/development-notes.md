# 개발 기록

우렁각시를 만들면서 실제로 실행한 것, 막혔던 곳, 측정한 수치를 정리한다. 보고서의 근거로 쓴다. 기능과 사용법은 [README](../README.md), 구조는 [architecture.md](architecture.md)에 있다.

기준: main `9a5a59a`(2026-11-25, PR #45 병합, v0.1.2 공개). 수치에는 **실측**(직접 잰 값), **참고**(이미 열어 본 평가셋으로 잰 값), **미검증**을 구분해 적는다. 측정은 모두 개발 PC 한 대(Core Ultra 5 226V, 8스레드, RAM 15.5GB, Windows 11)에서 했다. 사무용 PC에서 잰 값은 없다.

## 1. 한눈에

| 항목 | 값 |
|---|---|
| 기간 | 2026-10-24 첫 커밋 → 2026-11-25. PR 단위 개발은 11-09부터 |
| PR | 42개 병합(#1~#45 중 #12, #13은 이슈, #42는 닫고 #43으로 다시 올림) |
| 코드 | `src/` 약 9,900줄, `tests/` 23개 파일 약 8,800줄 |
| 시험 | 979 passed, 1 skipped(Windows). CI에서 Windows, Ubuntu, Docker 통과. ruff 통과 |
| CI | Windows, Ubuntu, Docker 3잡 + 배포 빌드. CI 실행 119회 중 성공 116회 |
| 배포 | v0.1.0(2026-11-24), v0.1.2(2026-11-25). GitHub Release에 Windows zip과 SHA-256 |
| 쓴 오픈소스 | llama.cpp(`b12125`), Qwen3.5-4B GGUF, Kiwi(kiwipiepy 0.24.1), PySide6, openpyxl, uv, PyInstaller |

처리 흐름은 다음과 같다: 한 줄 요청 → 요청 해석(코드 규칙 → 동의어표 → 로컬 모델 선택) → 대상 행 매칭과 자동 처리 판정 → 미리보기('확인 필요', '직접 처리') → [저장](작성한 칸만 바뀐 사본 + 근거 JSON).

## 2. 실제로 실행한 것

### 2.1 개발 환경과 시험

```powershell
uv sync --locked --extra dev     # 잠금 파일과 다르면 실패한다
./scripts/test.ps1               # pytest + ruff (Linux: scripts/test.sh)
uv run ureonggaksi               # 화면
```

- 새로 체크아웃한 폴더에서 처음 돌렸을 때 38개 중 33개가 실패했다. 내 PC에만 있던 캐시 경로 때문이었다. 고친 뒤 CI는 매 PR 새 체크아웃에서 돈다.
- 한국어 Windows(cp949)에서 `--help` 출력을 파일로 보내면 비정상 종료했다(긴 줄표 U+2014). 고쳤다.

### 2.2 Linux와 Docker

```sh
docker build -t ureonggaksi .
docker run --rm --network none ureonggaksi                  # 시험·린트
docker run --rm --network none ureonggaksi scripts/demo.sh  # prepare → commit, 원본 해시 확인
```

- 베이스 이미지는 digest로 고정하고, 컨테이너는 비루트 사용자로 실행한다. 네트워크 없이 돈다.
- 처음 빌드는 `.dockerignore`가 `.gitignore`를 따르지 않아 ruff 오류 4,213건이 났다. 고친 뒤 이미지 크기가 1.76GB에서 968MB로 줄었다(실측).
- 화면(PySide6)은 Linux에서 offscreen으로만 시험한다.

### 2.3 Windows 배포 빌드

```powershell
./scripts/build.ps1     # PyInstaller → 빌드 끝에 scripts/smoke_exe.py가 EXE로 시연 prepare 실행
```

- `--collect-data kiwipiepy_model`만으로는 모듈 코드가 빠져 EXE가 실행 중에 실패했다. 그래서 빌드 마지막에 EXE로 실제 요청을 돌리는 smoke 시험을 넣었다. `--hidden-import kiwipiepy_model`을 빼면 빌드가 실패하는 것을 확인했다(실측).
- 설치 폴더 약 225MB(Kiwi 모델 약 105MB 포함). 모델 GGUF 2.7GB는 따로 받는다.
- EXE에 코드 서명이 없다. SmartScreen, 백신 오탐 위험이 남아 있다.
- `v*` 태그를 push하면 GitHub Actions의 깨끗한 Windows 러너가 빌드하고, Python을 PATH에서 뺀 환경으로 EXE의 명령행, 화면 스모크 시험을 통과해야 초안 Release를 만든다. 영문 Windows(cp1252)에서만 드러난 한글 출력 결함 두 건을 여기서 찾았다.
- 올라간 zip은 다시 받아 SHA-256, 탐색기 압축 풀기(한글 파일 이름), 명령행, 화면 실행을 확인한 뒤 공개했다.

### 2.4 로컬 AI 실행

```powershell
uv run ureonggaksi prepare --request "발급번호 기준으로 신청인이랑 생일, 이수시간 채워줘" `
  --target examples/generated/demo/교육이수현황.xlsx --out 작업.plan.json `
  --runtime <llama-completion.exe> --model <Qwen3.5-4B-Q4_K_M.gguf> 이수확인서_*.hwpx
uv run ureonggaksi commit --plan 작업.plan.json --plan-hash <출력된 지문>
```

- 실행기는 llama.cpp 공식 릴리스 `b12125`의 `llama-completion`이다. 태그와 SHA-256으로 고정했다. GitHub의 'Latest' 릴리스에는 바이너리가 없었다.
- Qwen 공식 GGUF가 없어 제3자(unsloth) 양자화본을 커밋으로 고정해 쓴다.
- 질문 한 번에 약 14~18초 걸린다. 내역은 프로세스 시작 약 4초, 모델 적재 3.6초, 프롬프트 읽기 2.9초, 답 생성 5.4초다(실측). 제품 조건에서 질문 하나의 피크 메모리는 약 3.3GB이고, 두 물음을 동시에 띄우므로 작업 메모리는 그 두 배다.

### 2.5 평가 방법

평가셋은 모두 합성 자료다. 구현자가 열어 보지 않은 held-out을 별도로 만들어 쓴다. 한 번 열면 그 셋은 '참고'로 내려간다.

| 지표 | 뜻 | 기준 |
|---|---|---|
| S1 | 표시 없이 틀린 칸('확인 필요' 없이 틀린 열, 키) | 0(필수) |
| S2 | 물어야 할 요청 12건 중 규칙을 확정해 버린 수 | ≤ 2/12 |
| C | 기대 짝 64개 중 바른 열에 쓴 비율 | ≥ 50% |
| D | 미리보기 한 번의 지연(중앙값) | ≤ 30초 |

이 지표는 '확실한 칸만 채운다' 설계로 바꾼 뒤, 평가셋 s01c를 열기 전에 고정했다. 그전 지표는 '규칙 완전 일치 ≥ 80%'였다.

## 4. 난점

### 4.1 오프라인과 로컬 AI 실행기

- **문제:** 앱은 파이썬 audit hook으로 소켓을 막는다. 그래서 루프백 HTTP로 통신하는 Ollama, llama-server는 쓸 수 없다. 자식 프로세스에는 이 hook이 걸리지 않는다.
- **겪은 일:**
  - 처음 고른 `llama-cli`는 '표준 입출력' 도구로 보였다. 그런데 netstat으로 보니 실행 중에 `127.0.0.1`에서 LISTEN 중이었다.
  - `llama-completion`으로 바꾸니 `-sys`를 주면 비정상 종료했고, `-rea off`를 줘도 사고 과정 텍스트가 나왔다.
- **결정:** `llama-completion -no-cnv`에 `--offline`을 준다. 채팅 프롬프트는 코드가 직접 조립한다. 실행 중 소켓은 0건이었다(실측). 실행기는 내려받을 때 공식 릴리스의 SHA-256과 대조했다. 앱이 실행 시 해시를 검사하지는 않는다.

### 4.2 모델에게 맡길 몫

- **문제:** 모델이 규칙 JSON을 직접 쓰게 하자 형식은 12/12 맞는데 뜻은 5/12만 맞았다.
- **결정:**
  - 모델은 선택지(JSON 스키마 enum) 중에서 고르기만 한다. 규칙, 키, 작업 종류는 코드가 정한다.
  - 구조상 형식이 틀린 답이 나올 수 없다. 목록 밖 답은 버린다.

### 4.3 자연어 요청의 '빼기'를 놓치지 않기 (가장 오래 걸림)

- **문제:** "직급은 빼고", "현행 유지", "생일은 나중에" 같은 말을 놓치면 틀린 값이 결과 XLSX에 조용히 남는다.
- **겪은 일:**
  - **부정 표현 목록:** 검수할 때마다 새 표현에 뚫렸다. 검수 1~5차에 오확정이 21, 18, 30, 21, 10건 나왔다.
  - **4B에게 역할 판독을 맡김:** 공격 요청 167건 중 16건을 틀리게 확정해 버렸다.
  - **이름별 국소 판정(PR #18):** 검수 6회에서 지적이 10 → 13 → 13 → 8 → 4건으로 천천히 줄었다.
- **결정:**
  - 허용 목록으로 뒤집었다. 모르는 말이 섞이면 묻는다.
  - 이어서 '확실한 칸만 채운다'로 바꿨다. 모델이 고른 짝은 '확인 필요'로 보이고, 말하지 않은 키는 묻는다.
  - 마지막으로 조사와 부정은 형태소 분석기 Kiwi의 품사로 읽는다(PR #31). 정규식은 '평가는'을 '평'으로 잘랐고, 목록 밖의 '다 채우진 마'를 놓쳤다.

### 4.4 작성한 칸만 바뀐 XLSX

- **문제:** openpyxl로 다시 저장하면 수식 캐시값이 사라지고 수정 시각을 덮어쓴다. 확장 기능과 도형도 사라질 수 있다.
- **결정:**
  - 대상 시트 XML에서 쓸 `<c>` 요소만 바이트 위치로 바꾸고, 나머지 ZIP 항목은 그대로 복사한다(PR #15).
  - 저장 뒤 원본과 항목 목록, 바이트, 칸 지도, 재열기 값을 비교한다.
  - Excel에서 복구 창 없이 열리는 것을 확인했다(실측).
- **검수에서 잡힌 것:** 저장 단계(PR #16) 검수에서 수식 칸 여부를 압축된 ZIP 바이트에서 `<f`로 찾고 있어 늘 '수식 없음'으로 판정하는 버그가 잡혔다. 같은 검수에서, 같은 스냅샷끼리 비교해 늘 통과하던 검증도 지적됐다. 통과하는 검증이 실제로 무언가를 검사하는지 확인해야 한다는 것을 배웠다.

### 4.5 악성 XLSX 입력

- **문제:** 5KB 파일에 `ref="A1:XFD1048576"` 하나를 넣으면 openpyxl 로드가 60초 넘게 멈췄다.
- **겪은 일:** 정규식 사전 검사, 파서 필터, 요소 수 제한을 차례로 넣었지만 검수 5회(1차 + 재검수 4회) 동안 거의 매번 우회됐다(PR #9 시기).
- **결정:** 로드를 호출마다 새 작업자 프로세스에서 60초, 2GiB 상한(Windows Job Object, Linux RLIMIT_AS) 안에 돌린다(PR #14). 막는 규칙을 늘리지 않고 피해 범위를 가뒀다.

### 4.6 HWPX 글자 해석

- **시험:** 공개 hwpxlib 표본 49개로 시험했다. 48개를 읽었고, 거절한 1개는 외부 연결 패키지라 안전 규칙대로 막은 것이다.
  - 표 239개, 칸 5,708개에서 격자 불일치 0이었다(실측).
- **결함 두 개:**
  - 변경 추적에서 삭제된 글자를 값으로 읽었다.
  - 한글 특수 공백(nbSpace, fwSpace)을 지워 앞뒤 글자가 붙었다.
  - 둘 다 고쳤다(PR #7, #8). 변경 추적이 남은 칸은 추측하지 않고 '직접 처리'로 남긴다.

### 4.7 지연과 메모리

- **문제:** 같은 질문을 순서를 바꿔 두 번 묻는데(답이 같을 때만 믿는다), 차례로 물으면 32~42초 걸려 기준 30초를 넘었다.
- **결정:** 두 물음을 동시에 띄운다(PR #29). 21.6~29.2초로 기준 안에 들어왔다(실측).
- **대가:**
  - 작업 메모리가 두 배다.
  - 측정 중 메모리 부족으로 강제 종료가 여러 번 있었다.
  - 다른 작업과 겹쳐 잰 지연 값은 무효로 처리했다.
- 상주 서버(llama-server)는 포트와 수명 관리라는 새 보안 경계가 생겨 쓰지 않았다.

### 4.8 측정 자체의 함정

- **잘못된 실행 파일:** s01c 첫 측정은 하네스에 실행 파일을 잘못 넘긴 상태로 돌았다. 모델 호출이 매번 실패했는데, 제품은 설계대로 모델 없이 계속 진행해 겉으로는 정상처럼 보였다. 이 측정은 무효 처리했다.
- **조용한 실패:** 검수 스크립트가 출력 없이 실패한 적이 있다. '출력 없음'은 '문제 없음'이 아니다.
- **잘못 짚은 원인:** Kiwi를 넣은 뒤 메모리 상한 시험이 실패했다. 처음에는 부하 탓으로 봤다. 실제로는 kiwipiepy가 끌어온 numpy를 openpyxl이 불러온 것이었다. numpy를 설치하지 않도록 고정해 해결했다.

### 4.9 GitHub 설정

- **브랜치 삭제가 막힘:** 'Copilot code review'라는 이름의 규칙 세트에 실제로는 삭제, 강제 push 금지만 들어 있었다.
- **병합이 막힘:** 협업자가 1명인데 승인 1명이 필수라 어떤 PR도 병합할 수 없었다.
- **빨간 CI도 병합 가능:** Protect Main에 필수 상태 검사가 없어 CI가 실패해도 병합이 막히지 않았다. 지금은 `test (windows-2025)`, `test (ubuntu-24.04)`, `docker`를 필수로 등록했다.

## 5. 오래 걸린 곳

| 순위 | 작업 | 왜 오래 걸렸나 |
|---|---|---|

## 7. 남은 한계

- **사무용 PC 미실측:** 8GB 메모리 PC(모델 프로세스 2개), AVX2가 없는 CPU에서의 기동과 지연은 확인하지 않았다.
- **쓸모 지표 미달:** 처음 보는 자료(봉인 s02)에서 C 37%로 기준 50%에 못 미친다. s02도 측정 뒤 열어 고쳤으므로 지금 코드의 처음 보는 자료 성능은 따로 재지 않았다.
- **단위:** 열 머리글 끝 괄호의 단위만 읽는다. 표 위에 따로 적힌 단위, 금액이 아닌 단위끼리의 환산(km→m)은 하지 않는다.
- **4B 판독:** "직무는 나중에 따로 정할게", "X만" 같은 요청을 잘못 읽을 수 있다. 그 칸에는 '확인 필요'가 붙는다.
- **HWPX:** 한글 프로그램으로 만든 정답 문서와의 대조, 여러 문단에 걸친 변경 추적은 미검증이다.
- **오프라인 증명:** 소켓 관찰은 폴링 방식이라 짧은 연결을 놓칠 수 있다. 방화벽으로 막은 상태에서 실행한 시험은 하지 않았다.
- **공급망:** 모델 GGUF가 제3자 양자화본이다. EXE에 서명이 없다.

## 8. 교훈

- 스키마를 지킨 답이 맞는 답은 아니다(형식 12/12, 의미 5/12).
- 작은 모델에게는 쓰게 하지 말고 고르게 하라.
- 도구 설명을 믿지 말고 프로세스를 관찰하라(`llama-cli`의 루프백 서버).
- 위험한 표현을 목록으로 막으면 끝이 없다. 허용할 것만 정하라.
- 빠뜨린 칸은 이유를 남길 수 있지만, 틀린 칸은 조용히 남는다.
- 본 자료로 고친 점수는 부푼다(개발셋 14/24, 최고 23/24 → held-out 32%).
- 늘 통과하는 검증은 아무것도 검사하지 않는 것일 수 있다.
- 채점이 보지 않는 곳에서 결함이 난다(짝만 채점해 '원 단위 글자를 천원 열에 쓰는' 결함을 놓쳤다).
- 보안 주장은 문서가 아니라 시험에 묶는다(화면을 다시 만들며 빠진 장치를 배포 전 점검에서 찾았다).
