# 품질 평가

한 줄 요청을 규칙으로 바꾸는 해석 단계를 어떻게 평가했는지, 그리고 날짜별 결과를 적는다. 기준은 2026-11-25(v0.1.2)이다. 개발 과정의 서술은 [development-notes.md](../development-notes.md)에 있다.

## 1. 원칙

- **합성 자료만 쓴다.** 실제 업무 문서는 반출하지 않는다는 원칙에 따라 평가셋도 모두 합성 HWPX, XLSX와 합성 요청이다.
- **처음 보는 셋으로 판정한다(held-out).** 구현자가 열어 보지 않은 셋으로 잰 값만 판정에 쓴다. 한 번 열어 실패 사례를 보고 고치기 시작하면, 그 셋으로 잰 값은 **참고값**이 된다.
- **기준은 측정 전에 고정한다.** 결과를 본 뒤 기준을 바꾸지 않는다.
- **안전을 쓸모보다 먼저 본다.** 빠뜨린 칸은 이유를 남길 수 있지만, 틀린 칸은 결과 XLSX에 조용히 남는다.

|---|---|---|---|---|
| 합성 지시문 | 12사례, 문서 2종 | 구현자가 작성 | 2026-11-05 | 방식 비교용(실험) |
| s01 | 24사례(명단형 표 6) | 별도 작성 | 2026-11-12 | 개발셋 |

| s01c | 40사례(채우기 28, 질문 12), 기대 짝 64개 | 별도 작업자가 작성하고 검증 스크립트 통과 | 2026-11-20 | 개발셋(참고) |
| s02 | 40사례(채우기 28, 질문 12), 기대 짝 71개, 새 서식 4종 | 독립 작업자가 작성. 검증 스크립트 통과, 일부러 망가뜨린 정답 6개는 검증 실패 | 2026-11-24 | 봉인 측정 1회 뒤 개봉(참고) |

- s01c 기대 짝 64개 가운데 50개(78%)는 문서 항목과 열 이름이 다른 짝이다(예: '성명' → '신청인').
- '질문' 사례는 규칙이 서지 않아 사용자에게 물어야 맞는 요청이다.
- **봉인셋 운용:** 같은 셋을 보며 고치면 점수가 부푼다. 그래서 측정 전까지 내용(사례, 함정 목록)을 구현자가 열지 않는 봉인셋을 따로 만든다. s02가 그렇게 만든 첫 봉인셋이다. 2026-11-24 첫 측정 뒤 실패 분석을 위해 열었다. 최종 판정용 새 봉인셋(s03)을 만들기로 했지만, 2026-11-25 기준 s03 측정 결과는 없다.

## 3. 지표

2026-11-20 '확실한 칸만 채운다'로 설계를 바꾸면서 다음 지표를 정했다. s01c 결과를 보기 전에 고정했다.

| 지표 | 정의 | 기준 |
|---|---|---|
| **S1** 표시 없이 틀린 칸 | 채우기 사례에서 기대 짝이 아닌데 '확인 필요' 표시 없이 쓴 짝의 수. 기대와 다른데 표시가 없는 키도 센다 | **0(필수)** |
| **S2** 물어야 할 요청을 확정 | 질문 사례 12건 중 규칙을 만들어 버린 수 | ≤ 2/12 |
| **C** 채운 비율 | 채우기 사례의 기대 짝 가운데 바른 열에 쓴 비율. '확인 필요'로 표시된 짝도 포함한다 | ≥ 50% |
| **D** 지연 | 미리보기 한 번(`prepare`)의 중앙값 | ≤ 30초 |

- **C는 두 시점에서 잰다.** '첫 미리보기'는 요청만으로 낸 결과다. '키 답변 뒤'는 키 질문에 기대 답을 한 번 넣고 다시 돌린 결과다. 키를 말하지 않은 요청은 설계상 먼저 키를 묻기 때문에, 첫 미리보기만으로는 실제 사용 흐름을 대표하지 못한다.
- **참고로만 보는 것:** 옛 지표인 규칙 완전 일치, '확인 필요'로 표시된 틀린 짝 수, 질문 대상 일치.
- **이전 지표:** 2026-11-13에 정한 '규칙 완전 일치 ≥ 80%, 질문 정확도 ≥ 80%, 지연 중앙값 ≤ 30초'였다. 모델 추정까지 확정하는 설계를 전제로 한 지표라, 질문과 빈칸이 늘어나는 것이 의도된 동작인 새 설계에는 맞지 않았다.

### 3.1 값 단위 검사(2026-11-24 추가)

v0.1.0 공개 직후 결함을 찾았다. 짝은 맞는데 값이 틀린 경우였다. 문서 '피해액 4,350,000원'을 열 '피해추산액(천원)'에 글자 그대로 썼다. 짝 단위로 채점하는 C와 S1은 이 결함을 보지 못했다. 짝이 맞고 '확인 필요' 표시도 붙어 있었기 때문이다.

그래서 단위가 붙은 열(머리글 괄호의 원, 천원, 만원, ㎡ 등)에 실제로 쓴 값이 열 단위의 숫자인지 검사하는 도구를 더했다. 짝은 정답대로 주고(가짜 모델), 쓰인 칸의 값만 본다. 결과가 열 단위 숫자가 아닌 칸을 BAD로 센다. 기준은 0이다.

## 4. 측정 조건

- 실제 제품 흐름(`service.prepare`)에 Qwen3.5-4B Q4_K_M을 붙였다. 실행기는 llama.cpp `b12125` `llama-completion`(`--offline --temp 0`)이다.
- 사례마다 1회만 돌렸다.
- 개발 PC 한 대에서 쟀다(Core Ultra 5 226V, 8스레드, RAM 15.5GB, Windows 11).
- 측정 중 다른 무거운 작업이 겹친 실행의 지연 값은 무효로 처리했다. 아래 표의 D는 단독으로 잰 값만 적는다.

## 6. 읽는 법과 한계

- **처음 보는 데이터에서는 안전만 일반화됐다.** s02 봉인 측정에서 S1 0, S2 0/12는 유지됐다. 그러나 C는 키 답변 뒤 37%로, 같은 시점 s01c의 67%에 크게 못 미쳤다. s01c 수치는 그 셋의 실패를 보며 고친 결과라 낙관적이다(동의어표 확장 등).
- **판정할 수 있는 최종 held-out 수치가 없다.** s02는 측정 뒤 열어 개발셋으로 썼다. 그래서 마지막 s02 수치 18% / 42%는 참고값이다. 처음 보는 셋에서 잰 마지막 C는 봉인 측정의 17% / 37%다.
- **C 기준(50%)은 s01c(참고)에서만 넘었다.** s02에서는 키 답변 뒤에도 42%로 미달이다.
- **D는 중앙값만 기준 안이다.** 최대 지연은 30초를 넘는 사례가 있다(예: s02 봉인 측정 최대 58.8초). 모델을 실제로 부르는 요청이 느리다.
- **사례당 1회 측정이다.** `--temp 0`이지만 반복 측정으로 편차를 재지 않았다. 질문 구성이 바뀌면 같은 이름에 대한 4B의 답이 바뀌는 것을 여러 번 관찰했다.
- **합성 자료만 썼다.** 평가셋은 별도 작업자가 만들었지만 같은 프로젝트 안에서 만들었다. 실제 공공 서식과 실제 사용자 말투에서의 성능은 모른다.
- **측정 PC가 하나다.** RAM 8GB 사무용 PC에서는 지연, 메모리를 재지 않았다. 측정 중 메모리 부족으로 실행이 강제 종료된 적이 여러 번 있어, 그 실행은 이어 돌리거나 다시 쟀다.
- **짝 단위 채점은 값 변환 결함을 못 본다.** 그래서 값 단위 검사를 따로 둔다(3.1절). 날짜 형식 등 다른 값 변환은 이 검사가 보지 않는다.
