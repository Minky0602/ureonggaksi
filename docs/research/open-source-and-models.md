## 1. HWPX 읽기

| 후보 | 판단 |
|---|---|
| 직접 파서(`zipfile` + defusedxml) | **채택** |
| [python-hwpx](https://github.com/airmang/python-hwpx) | 검토 후 런타임 의존성으로 쓰지 않음 |

- **확인한 것(2026-11-09):** 공개 저장소 `neolord0/hwpxlib`(Apache-2.0, 커밋 `f9fd2255`)의 시험 파일 49개를 파서에 그대로 넣었다. 48개가 실제 한글 프로그램 저장본이다.
  - 읽기 48/49. 거절한 1개는 외부 연결 패키지라 안전 규칙대로 막은 것이다.
  - 표 239개, 칸 5,708개(병합 490개)에서 파일에 적힌 행, 열 수와 칸 격자가 모두 맞았다.
  - 결함 2개가 나왔다. 변경 추적에서 삭제된 글자를 값으로 읽었고, 한글 특수 공백(`nbSpace` 93개, `fwSpace` 59개)을 지워 앞뒤 글자가 붙었다.
- **결정(2026-11-10):** 직접 파서를 유지하고 두 결함을 고쳤다(PR #7, #8). 특수 공백은 공백으로 읽는다. 변경 추적이 남은 칸은 추측하지 않고 비운 뒤 이유를 알린다. 이 두 동작을 직접 제어해야 해서 python-hwpx로 바꾸지 않았다.
- XML 위험 기능(엔티티 확장 등)은 [defusedxml](https://github.com/tiran/defusedxml)로 막는다. ZIP 항목 수, 압축률, 크기 한도는 앱이 따로 검사한다.
- **남은 한계:** 한글 프로그램으로 만든 정답 문서와의 칸별 대조, 여러 문단에 걸친 변경 추적은 확인하지 않았다. 표본은 개발자 시험, 버그 제보 파일이라 공공 서식 전체를 대표하지 않는다.

## 2. XLSX 읽기와 쓰기

### 2.1 읽기

| 후보 | 판단(2026-11-11) |
|---|---|
| [openpyxl](https://openpyxl.readthedocs.io/en/stable/) 3.1.5 | **채택.** 수식, 배열 수식, 병합, 시트 보호, 셀 잠금을 읽을 수 있다 |
| python-calamine | 제외. 수식, 병합, 보호 정보가 없다 |
| `pandas.read_excel` | 제외. 머리글, 셀 주소를 잃고 의존성이 크다 |
| xlrd | 제외. xlsx를 지원하지 않는다 |

- **실측(2026-11-11):** 배열 수식은 앵커 칸만 수식으로 보이고 범위 안 나머지 칸은 일반 칸처럼 보인다. 그래서 `ws.array_formulae`로 범위 전체를 막는다. 수식 칸은 수식 판정용과 캐시값용으로 두 번 연다.
- **악성 입력:** 5KB 파일의 `ref="A1:XFD1048576"` 하나로 openpyxl 로드가 60초 넘게 멈췄다. 사전 검사를 다섯 차례 고쳐도 다른 표기로 우회됐다. 2026-11-12부터 로드를 호출마다 새 작업자 프로세스에서 60초, 2GiB 상한 안에 돌린다(PR #14, Windows Job Object, Linux `RLIMIT_AS`).
  - psutil 감시는 사후 감시이고 새 바이너리 의존성이라 제외했다. pebble은 메모리 상한이 없어 제외했다.

### 2.2 쓰기

결과 XLSX는 "작성한 칸만 다른 사본"이어야 한다.

| 후보 | 판단 |
|---|---|
| openpyxl로 다시 저장 | 제외(2026-11-09). 실측에서 수식 캐시값이 사라졌다(`<v>0</v>` → `<v />`). 저장할 때마다 `docProps/core.xml`의 수정 시각을 덮어쓴다. 공식 문서상 도형, 그림, x14 확장(조건부 서식, 데이터 유효성, 스파크라인)도 잃을 수 있다 |
| XlsxWriter | 제외. 쓰기 전용이라 기존 파일을 고칠 수 없다 |
| lxml로 다시 직렬화 | 제외. 바이트가 바뀌고 바이너리 의존성이 는다 |
| xlsxedit(Apache-2.0) | 같은 접근의 참고 구현이다. 작은 단일 저자 저장소라 의존성으로 쓰지 않고 방식만 참고했다 |
| **직접 구현한 최소 변경 쓰기** | **채택.** 대상 시트 XML에서 쓸 `<c>` 요소만 바이트 위치로 바꾸고, 나머지 ZIP 항목은 그대로 복사한다 |

- **실측(2026-11-12, PR #15):** Excel로 만든 시험 파일(도형, x14 데이터 막대, 수식 캐시값, 공유 문자열, 병합, 시트 보호, calcChain)에 칸 3개를 썼다. 바뀐 ZIP 항목은 시트 XML과 `workbook.xml`(재계산 표시)뿐이었다. 이 PC의 Excel에서 복구 창 없이 열렸고, 수식도 다시 계산됐다.
- openpyxl은 저장 뒤 결과를 다시 열어 원본과 비교하는 검증에만 쓴다.
- **남은 한계:** 한셀, LibreOffice, Google 내보내기로 만든 취합표에서는 확인하지 않았다.

## 4. 로컬 LLM 실행기

앱은 파이썬 audit hook으로 인터넷 소켓(루프백 포함)을 막는다. 그래서 HTTP로 통신하는 실행기는 그대로 연결할 수 없다.

| 후보(2026-11-05 공식 문서로 비교) | 판단 |
|---|---|
| A. llama-cpp-python(앱 프로세스 안) | 제외. 공식 PyPI에는 소스 배포본만 있고, 미리 빌드된 Windows 패키지는 관리자 개인 저장소에서 받아야 한다. 모델이 죽으면 화면까지 함께 죽는다 |
| B. llama.cpp 공식 실행 파일을 자식 프로세스로 | **채택** |
| C. [Ollama](https://docs.ollama.com/capabilities/structured-outputs) | 제외. 별도 설치가 필요하고, 자동 업데이트와 클라우드 기능이 기본으로 켜져 있어 앱이 오프라인을 보장할 수 없다. 루프백 HTTP가 필요하다([FAQ](https://docs.ollama.com/faq)) |
| `llama-server`(상주 서버) | 제외(2026-11-21). 적재, 초기화 약 7초를 줄일 수 있지만, 포트와 수명 관리라는 보안 경계가 새로 생긴다 |

[llama.cpp](https://github.com/ggml-org/llama.cpp)를 쓰며 확인한 것:

- **버전 고정(2026-11-05):** GitHub의 'Latest' 릴리스에는 바이너리가 없었다. Windows 바이너리는 `bNNNN` 태그에 있다. `b12125`로 고정했다. `llama-b12125-bin-win-cpu-x64.zip`(24,730,921바이트)은 GitHub가 제공하는 SHA-256과 대조했다. 앱이 실행할 때 해시를 검사하지는 않는다.
- **`llama-cli`를 버림(2026-11-05):** 표준 입출력 도구로 보였지만, 실행 중 `netstat`으로 보니 `127.0.0.1`의 임의 포트에서 LISTEN하고 있었다. JSON 스키마 문법이 채팅 템플릿 토큰과 충돌하는 오류도 났다.
- **`llama-completion` 사용법:** `-sys`를 주면 비정상 종료(0xC0000409)했고, `-rea off`를 줘도 사고 과정 텍스트가 나왔다. 그래서 `-no-cnv --offline`으로 실행하고, Qwen ChatML 프롬프트(빈 `<think>` 블록 포함)를 코드가 직접 조립한다. 이 방식에서 stdout에는 JSON만 나왔고, 실행 중 소켓은 0건이었다(netstat 폴링).
- **출력 제약:** `-jf`(JSON 스키마 파일)로 선택지를 enum으로 묶는다. 모델은 선택지에서 고르기만 하고, 규칙, 키, 작업 종류는 코드가 정한다(5절).
- **지연(2026-11-21):** 질문 한 번에 약 14~18초 걸린다. 내역은 프로세스 시작 약 4초, 모델 적재 3.6초, 프롬프트 읽기 2.9초, 답 생성 5.4초다. 순서를 바꾼 같은 질문 두 개를 동시에 띄워(PR #29) 모델을 쓰는 요청이 38.5초 / 32~40초 / 42초에서 23.1초 / 21.6초 / 29.2초로 줄었다. 대신 작업 메모리가 두 배가 된다.
- **배포:** 실행기와 모델은 앱에 넣지 않는다. 사용자가 받아 경로를 고른다. 모델, 채팅 형식, 실행기 빌드를 한 묶음으로 고정하고, 바꿀 때는 회귀 시험을 다시 돌린다.

## 5. 모델 선택과 크기

Qwen 조직은 Qwen3.5 공식 GGUF를 내지 않았다(2026-11-05 Hugging Face API로 확인). 그래서 제3자 양자화본 `unsloth/Qwen3.5-*-GGUF`(Apache-2.0, 원본 `Qwen/Qwen3.5-*`)를 커밋으로 고정해 쓴다. 파일은 Hugging Face LFS sha256으로 대조했다.

| 모델(Q4_K_M) | 고정 커밋 | 파일 크기 |
|---|---|---|
| 2B | `f6d5376b` | 약 1.3GB |
| [4B](https://huggingface.co/unsloth/Qwen3.5-4B-GGUF)(원본 [Qwen/Qwen3.5-4B](https://huggingface.co/Qwen/Qwen3.5-4B)) | `e87f1764` | 약 2.7GB |
| [9B](https://huggingface.co/unsloth/Qwen3.5-9B-GGUF) | `3885219b6810b007914f3a7950a8d1b469d598a5` | 5,680,522,464바이트 |

### 5.1 비교 측정

모두 llama.cpp `b12125`, `--temp 0`, `--offline`, 개발 PC에서 쟀다.

**① 모델에게 무엇을 맡길까(2026-11-05, 합성 지시문 12개)**

| 방식 | 모델 | JSON 형식 | 규칙 검증 통과 | 값 정답 | 지연 중앙값 | 최대 메모리 |
|---|---|---|---|---|---|---|
| 모델이 규칙 JSON을 직접 작성 | 2B | 12/12 | 11/12 | 5/12 | 8.7초 | 2.0GB |
| 모델이 규칙 JSON을 직접 작성 | 4B | 12/12 | 9/12 | 5/12 | 19.0초 | 4.4GB |
| 모델은 블록 번호만 고르고 규칙은 코드가 작성 | 2B | 12/12 | 12/12 | 9/12 | 4.9초 | 2.0GB |
| 모델은 블록 번호만 고르고 규칙은 코드가 작성 | 4B | 12/12 | 12/12 | **12/12** | 9.9초 | 4.4GB |

형식(스키마)은 늘 맞았지만 뜻은 5/12만 맞았다. 모델 크기보다 역할을 좁히는 것이 효과가 컸다.

**② 한 줄 요청 전체를 모델이 고르게 할 때(2026-11-12, held-out s01 24사례)**

| 모델 | 완전 일치 | 키 | 항목 정밀도/재현율 | 지연 중앙값(최대) | 최대 작업 메모리 |
|---|---|---|---|---|---|
| 4B | 3/24 | 4/20 | 49% / 84% | 28.1초(65.8) | 4,445MB |
| 2B | 2/24 | 10/20(거의 늘 블록 1) | 17% / 32% | 13.6초(26.6) | 2,033MB |

두 모델 모두 애매한 요청에 '모름'을 한 번도 내지 않았다. 이후 작업 종류와 키는 코드가 정하고, 모델은 항목 짝 선택만 맡도록 바꿨다.

**③ 4B와 9B(2026-11-18, s01b 40사례, 이미 열어 본 셋이라 참고값)**

| 모델 | 완전 일치 | 표시 없이 틀린 짝 | 지연 중앙값 / 최대 | 대표 질문 최대 메모리 |
|---|---|---|---|---|
| 4B | 21/40 = 52% | 0 | 19.5초 / 87초 | 3.27GB |
| 9B | 22/40 = 55% | 0 | 45.2초 / 144초 | 5.03GB |

### 5.2 결정

- **4B를 기본으로 쓴다.** 2B는 항목 짝 선택이 크게 떨어졌다. 9B는 1사례(+3%p)를 더 맞혔지만 지연 중앙값이 기준(30초)을 넘고, 메모리가 5GB를 넘으며, 파일이 두 배다. 대상이 RAM 8GB 사무용 PC라 맞지 않다고 판단했다(사무용 PC는 미실측).
- 9B 모델 카드는 기본이 생각(thinking) 모드라고 적고 있다. 제품 프롬프트는 생각 단계를 비워 두며, 실측에서 JSON 답만 나왔다.
- **임베딩 모델 제외(2026-11-22):** Qwen3-Embedding-0.6B(공식 GGUF Q8_0 639MB, Apache-2.0)를 검토했다. 한국어 동의어 매칭 근거가 모델 카드에 없고 RAM 부담이 커서 보류했다. bge-m3와 multilingual-e5는 공식 GGUF가 없었다.
- **알려진 한계:** 4B는 "직무는 나중에 따로 정할게", "X만" 같은 빼기, 미루기를 '채움'으로 읽을 수 있다. 그래서 확정할 수 있는 부분은 코드(6절)로 옮겼고, 모델이 고른 짝에는 '확인 필요'를 붙인다.

## 6. 요청 해석: 정규식에서 Kiwi로

"직급은 빼고", "생일은 나중에", "다 채우진 마" 같은 빼기, 미루기를 놓치면 틀린 값이 조용히 남는다.

| 시기 | 방식 | 결과 |
|---|---|---|
| 2026-11-13 ~ 11-16 | 부정 표현 목록(정규식) | 검수마다 새 표현에 뚫렸다. 오확정 21 → 18 → 30 → 21 → 10건 |
| 2026-11-16 | 4B에게 이름별 역할 판독을 맡김 | 공격 요청 167건 중 16건을 틀리게 확정. 빼라는 뜻을 '채움'으로 읽었다 |
| 2026-11-16 ~ | 허용 목록으로 뒤집음(모르는 말이 섞이면 묻는다) | 오확정은 막았지만 실제 표현에서 질문이 크게 늘었다 |
| **2026-11-22 ~** | **조사, 어미, 부정은 Kiwi 품사로 읽음**(PR #31) | 정규식은 '평가는'을 '평'으로 잘랐고 '다 채우진 마'를 놓쳤다. Kiwi는 '평가/NNG 는/JX', '채우/VV 지/EC ㄴ/JX 말/VX'로 가른다 |

Kiwi 조사(2026-11-22, 공식 저장소, PyPI):

- [kiwipiepy](https://github.com/bab2min/kiwipiepy)는 0.24부터 코드와 모델이 모두 Apache-2.0이다(0.23.2 이하는 LGPL). 확장 모듈에 정적 링크된 Eigen(MPL-2.0) 등의 NOTICE를 배포물에 유지해야 한다.
- 0.25.0, 0.25.1은 PyPI에서 회수(yank)됐다. 그래서 0.24.1과 kiwipiepy_model 0.24.0으로 고정했다.
- 크기: Windows 휠 3.9MB, 모델 패키지 설치 후 105MB.
- 실측: `load_multi_dict=False`로 적재 2.1초, 상주 메모리 +277MB(working set). 첫 분석 뒤 문장당 1ms 미만.
- 한계: 사전에 없는 복합 이름은 쪼갠다(이수시간 → 이/수/시간). 그래서 이름 찾기는 기존 코드가 하고, Kiwi는 기능어(조사, 어미, 보조 용언, 부사)만 읽는다.
- **numpy 제외:** kiwipiepy는 학습 도구용으로 numpy를 요구한다. 그런데 numpy가 설치돼 있으면 openpyxl이 불러와서, 메모리 상한을 건 XLSX 작업자에서 할당 실패가 났다. `[tool.uv] override-dependencies`로 numpy를 설치하지 않는다. 형태소 분석에는 numpy가 필요 없다.
- 효과: s01c(참고값)에서 C가 기존과 같았다(첫 미리보기 19%, 키 답변 뒤 31%). 점수를 올리려는 변경이 아니라 같은 점수에서 표현 목록을 구조 규칙으로 바꾼 것이다.

## 7. 패키징(Windows)

- **PyInstaller onedir**(6.22.3)로 만든다. PyInstaller는 GPL이지만 부트로더 배포 예외가 있다.
- **설치 폴더 약 225MB**이고, 그중 Kiwi 모델이 약 105MB다. 모델 GGUF 2.7GB는 따로 받는다.
- **Kiwi 모듈 누락(2026-11-22):** `--collect-data kiwipiepy_model`만으로는 모듈 코드가 빠져 EXE가 실행 중에 실패했다. `--hidden-import kiwipiepy_model`로 고쳤다. 빌드 마지막에 `scripts/smoke_exe.py`가 EXE로 합성 시연을 실제로 돌린다. hidden-import를 빼면 빌드가 실패하는 것을 확인했다.
- **Release 자동화(2026-11-24, PR #43):** 태그를 올리면 GitHub Actions(windows-2025)가 빌드와 smoke를 돌리고 초안 Release를 만든다. smoke는 PATH에서 Python, uv를 뺀 환경으로 실행한다.
  - 영문 Windows 러너(cp1252)에서만 드러난 결함 2건을 여기서 찾았다. 빌드 스크립트의 한글 경로 출력, EXE 명령행의 한글 출력이다. 둘 다 고쳤다.
- **라이선스 수집:** `scripts/collect_licenses.py`가 각 배포 패키지의 라이선스 파일을 복사한다. 하나도 없으면 빌드를 실패시킨다. 2026-11-09에 영국식 철자 `LICENCE`를 놓쳐 openpyxl 등이 0개로 나오던 것을 고쳤다.
- **남은 한계:** 코드 서명이 없다(SmartScreen, 백신 오탐 위험). AVX2가 없는 CPU와 RAM 8GB PC에서는 실행을 확인하지 않았다.

## 8. 환경과 잠금

- [uv](https://docs.astral.sh/uv/guides/integration/github/) 0.13.5와 `uv.lock`을 쓴다. `uv sync --locked --extra dev`는 잠금 파일과 다르면 실패한다.
- pip 사용자를 위해 `requirements.lock.txt`도 둔다. pip는 uv의 numpy 제외를 모르므로 `--no-deps`로 설치해야 한다.
- **깨끗한 환경 재현(2026-11-09):** 커밋된 내용만으로 새로 체크아웃하자 시험 38개 중 33개가 실패했다. pytest 임시 경로가 개발 PC에만 있는 폴더에 기대고 있었다. 고친 뒤 Windows 새 복제와 빈 Ubuntu 24.04 컨테이너에서 모두 통과했다.

## 9. CI와 Docker

- **CI:** GitHub Actions `test (windows-2025)`, `test (ubuntu-24.04)` 2잡으로 시작했고(2026-11-09), `docker` 잡을 더했다(2026-11-21). 액션은 커밋 SHA로 고정한다. 2026-11-21부터 세 잡을 main 병합의 필수 검사로 등록했다. 그전에는 CI가 실패해도 GitHub가 병합을 막지 않았다.
- **Docker(2026-11-21, PR #25):**
  - 기반 이미지 `python:3.12-slim-bookworm`과 uv 이미지를 digest로 고정한다. 비루트 사용자로 실행하고, 시험과 시연은 `--network none`으로 돈다.
  - 모델은 이미지에 넣지 않는다(모델 없이 해석하는 경로).
  - 실측: 시험 531 passed, 4 skipped(로컬 모델, Excel, Windows 경로 전용 시험). 시연은 채울 칸 8, 직접 처리 1, 확인 필요 2였고 원본 해시는 그대로였다.
  - 첫 빌드는 `.dockerignore`가 `.gitignore`를 따르지 않아 로컬 캐시가 들어갔고, ruff 오류 4,213건이 났다. Git이 무시하는 폴더를 빌드 맥락에서 빼자 이미지가 1.76GB에서 968MB로 줄었다. 검수 뒤 `.dockerignore`를 허용 목록으로 바꿔 `.env` 같은 파일이 들어갈 길도 막았다.
- Linux에서 화면(PySide6)은 offscreen으로만 시험한다. 빈 Ubuntu 24.04에는 시스템 라이브러리 6개(`libgl1 libegl1 libxkbcommon0 libglib2.0-0 libdbus-1-3 libfontconfig1`)가 필요했다.
