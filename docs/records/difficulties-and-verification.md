# 구현 난점과 검증 기록

개발 중 생긴 불확실성, 예상과 다른 동작, 설계 난점과 그것을 어떻게 시험했는지를 날짜순 항목(DIF-001~081)으로 남긴 기록이다.
각 항목은 문제, 시험, 확인 방법, 결과, 결정, 2026-11-25(v0.1.2) 기준 최종 상태로 정리했다. 결론이 나중에 바뀐 항목은 최종 상태에 바뀐 결과를 적었다.
최종 보고서의 '구현 중 어려움'과 배포 판단의 근거로 쓴다. 사용자가 알아야 하는 한계는 [README](../../README.md)와 [SECURITY.md](../../SECURITY.md)에도 있다.

**표기**

- `실측`: 적힌 명령, 자료로 직접 확인한 결과. `문서 확인`: 공식 문서, 저장소를 읽고 확인한 내용. `미검증`: 확인하지 못한 사항.
- 측정 환경은 따로 적지 않으면 개발 PC(Intel Core Ultra 5 226V, 8스레드, RAM 15.5GB, 한국어 Windows 11)다. 사무용 PC 성능으로 바꿔 말하지 않는다.
- 로컬 AI 측정 조건은 따로 적지 않으면 llama.cpp b12125 `llama-completion`, Qwen3.5-4B Q4_K_M, `--offline --temp 0`이다.
- 평가셋(s01, s01b, s01c, s02)은 모두 합성 자료이며 저장소에 넣지 않았다. 지표 정의는 [DIF-052](#dif-052)에 있다.
- 시험 수(`passed`)는 그 시점의 전체 시험 수다.

<a id="dif-001004"></a>
### DIF-001·004 · 로컬 AI 연동 방식과 자식 프로세스의 차단 범위 (2026-11-05)

- **문제:** 앱의 오프라인 가드(`offline.py`, 감사 훅)는 AF_INET/AF_INET6 소켓 생성과 `connect`, `bind`를 막는다. 그래서 루프백 HTTP를 쓰는 Ollama, llama-server를 그대로 붙일 수 없다. 반대로 자식 프로세스에는 이 가드가 적용되지 않는다.
- **시험, 확인:** `문서 확인`(2026-11-05) A. llama-cpp-python을 앱 안에서 실행, B. llama.cpp 공식 실행 파일을 자식 프로세스로 호출, C. Ollama에 루프백 접속.
- **결과:** A는 PyPI에 소스만 있고 미리 빌드된 Windows 패키지는 개인 저장소에서 받아야 하며, 모델 크래시가 GUI까지 죽인다. C는 별도 설치, 자동 업데이트, 클라우드 기능이 기본으로 켜져 있어 오프라인을 보장할 수 없다.
- **결정:** B를 채택했다. 자식 프로세스는 세 겹으로 다룬다. `--offline`과 로컬 `-m` 경로만 넘기고 다운로드 옵션(`-hf`, URL)은 넘기지 않는다. 출처를 확인한 공식 릴리스만 쓰도록 안내한다. OS 방화벽 정책을 함께 권고한다.
- **최종 상태:** B 방식이 제품에 들어갔다. 측정마다 자식 프로세스의 소켓은 0건이었다. 다만 netstat 폴링 간격(약 0.3~0.7초)보다 짧은 연결은 놓칠 수 있고, `llama-common.dll`이 `WS2_32.dll`을 참조한다. 방화벽으로 막은 상태의 실행은 `미검증`이다. 실행 파일 해시 확인은 구현하지 않았고 SECURITY에 "출처를 확인한 파일만 지정"으로 적었다.

<a id="dif-002003"></a>
### DIF-002·003 · llama.cpp 바이너리와 Qwen3.5 GGUF의 공급원 (2026-11-05)

- **문제:** llama.cpp의 GitHub 'Latest' 릴리스(`v0.9.0`)에는 바이너리 없이 `nightly-tag.txt`만 있다. Hugging Face `Qwen/` 조직에는 Qwen3.5 공식 GGUF가 없다(`Qwen/Qwen3.5-4B-GGUF`, `ggml-org/Qwen3.5-4B-GGUF` 없음).
- **시험, 확인:** `gh api repos/ggml-org/llama.cpp/releases/latest`, `.../releases?per_page=5`, Hugging Face API `api/models?author=Qwen&search=Qwen3.5`. `실측`
- **결과:** Windows 바이너리는 거의 매일 나오는 `bNNNN` 태그에 있고 자산마다 SHA-256 digest가 있다(`llama-b12125-bin-win-cpu-x64.zip` 24,730,921B). 쓸 수 있는 GGUF는 제3자 양자화본 `unsloth/Qwen3.5-{2B,4B}-GGUF`(Apache-2.0, base_model `Qwen/Qwen3.5-4B`)였다. 커밋을 고정하고(2B `f6d5376b`, 4B `e87f1764`) LFS sha256으로 대조했다.
- **결정:** 태그 하나(b12125)와 해시로 고정하고 'Latest'를 따라가지 않는다. 제3자 변환본은 공급망 위험이므로 배포에 넣는다면 공식 가중치에서 직접 변환하는 방안을 우선 검토한다.
- **최종 상태:** 런타임과 모델 모두 앱에 넣지 않고 사용자가 지정한다. 시험한 조합(b12125, unsloth 4B Q4_K_M)을 README와 THIRD_PARTY_NOTICES에 적었다. 직접 변환은 하지 않았다. 버전을 올릴 때는 회귀 시험과 소켓 0건 시험을 다시 돌린다.

<a id="dif-006"></a>
### DIF-006 · `llama-cli`가 실행 중 루프백 HTTP 서버를 띄움 (2026-11-05)

- **문제:** 방식 B는 "소켓 없이 표준 입출력만 쓴다"를 전제로 골랐다.
- **시험, 확인:** spike 하네스로 실행 중 `netstat -ano`를 0.3초 간격으로 보며 해당 PID의 연결을 모았다.
- **결과:** `실측` b12125 `llama-cli`가 `127.0.0.1:<임의 포트>`에서 LISTEN하고 자기 자신에게 접속했다(외부 주소 없음). stdout에 배너, 안내가 섞였고, JSON schema 문법이 채팅 템플릿 토큰과 충돌했다(`Unexpected empty grammar stack after accepting piece: <|im_start|>`).

### DIF-020 · 규칙 세트가 브랜치 삭제와 병합을 막음 (2026-11-09)

- **문제:** main이 아닌 브랜치 삭제가 `GH013 ... Cannot delete this branch`로 거부됐다.
- **시험, 확인:** `gh api repos/Minky0602/ureonggaksi/rulesets`와 상세를 읽기 전용으로 조회했다. `실측`
- **결과:** 'Copilot code review'라는 규칙 세트가 실제로는 모든 브랜치(`~ALL`)에 삭제, force push 금지만 걸고 있었다. 'Protect Main'은 승인 1명 필수에 우회가 없었고 협업자가 한 명이라, 작성자가 자기 PR을 승인할 수 없어 어떤 PR도 병합할 수 없었다. 병합 방식은 squash만 허용됐다.
- **결정:** 'Protect Main'에 삭제, force push 금지를 다시 넣은 뒤 이름과 다른 규칙 세트를 지웠다(순서를 바꾸면 main 보호가 사라진다). 'Protect Main'의 필수 승인 수를 0으로 내리고 승인 규칙은 관리자 우회가 있는 'Require code review'에만 남겼다. 우회 목록에 넣으면 나중의 CI 조건까지 건너뛰게 되어 쓰지 않았다.
- **최종 상태:** 해결. 2026-11-21에 필수 상태 검사가 없어 CI가 빨개도 병합이 막히지 않는다는 것을 발견했고, 지금은 'Protect Main'에 `required_status_checks`가 등록돼 있다. 배운 점: 보호 규칙은 만든 직후 실제 push, 삭제, 병합으로 시험한다. 혼자 쓰는 저장소에 '승인 1명 필수'를 우회 없이 걸면 스스로 잠긴다.
